第三方登录接入方案分析
Google / Facebook / Apple 登录 · WebGL & iOS 场景
1. 背景说明 2. 竞品分析 3. 推荐方案

1背景说明

第三方登录（Google / Facebook / Apple）在不同平台上的原生支持程度不同，这是本次调研和方案选型的出发点：

平台原生 Google 登录支持说明
Android 原生支持 可直接调用系统原生的 Google 登录方式，无需额外方案
WebGL（浏览器） 不支持原生 没有"原生"这个概念，必须通过 JS 方式实现登录
iOS 不支持原生 没有对应的原生调用方式，同样需要通过 JS 方式实现

因此本次方案调研聚焦在 WebGL 和 iOS 这两个需要额外接入方式的场景，Android 不在本次范围内。

2竞品 Google 登录分析

持续补充中：针对有 Google 登录功能的竞品游戏，抓包分析其具体采用的技术方案。

竞品 1 · Mega Hit Poker
megahitpoker.com
✓ 支持 Google 登录 · 采用 Firebase Auth 对接

证据（浏览器 Network 抓包）

  • 登录请求打到 identitytoolkit.googleapis.com/v1/accounts:signInWithIdp —— 这是 Firebase Identity Toolkit 的专属接口
  • 请求里的 requestUri 指向 https://mega-hit-poker.firebaseapp.com/__/auth/handler —— 这个 __/auth/handler 路径是 Firebase Auth 自动托管的登录中转页，是 Firebase 的特征标识
  • 返回结果里带有 idToken、refreshToken、oauthAccessToken、oauthIdToken 等字段，字段命名和结构与本项目 Firebase Auth Demo 实测结果完全一致
signInWithIdp 接口返回内容，可见 idToken / refreshToken
请求参数中的 requestUri 指向 firebaseapp.com 的 auth handler
竞品 2 · WSOP（World Series of Poker）
playwsop.com
✓ 支持 Google 登录 · 直连 Google Identity Services，未使用 Firebase

登录交互：One Tap 自动弹出 + 按钮弹窗，两条独立入口

进入页面会先自动弹出 Google 原生的账号选择卡片（One Tap / FedCM），这是用 google.accounts.id.prompt() 实现的自动入口；页面上的"GOOGLE SIGN-IN"按钮是另一条独立的入口，从页面加载起就一直存在，点击后会触发传统的 OAuth 弹窗。关掉 One Tap 卡片后点按钮能弹窗，只是切换到了这条本来就写好的路径，并不是 GIS 库检测到 One Tap 被关闭后自动切换的"降级"行为——这两条入口是 WSOP 前端各自独立实现的。

另外 Google One Tap 本身确实有真实的冷却机制：用户关闭/多次忽略后，Google 会在一段时间内不再自动弹出 One Tap（这个状态由 Google 侧控制），但它只影响"下次是否自动弹出"，跟按钮点击触发弹窗这件事没有关系。

页面自动弹出的 One Tap 账号选择卡片
关闭 One Tap 后，点击按钮改用的传统 OAuth 弹窗

证据：解码登录后拿到的 idToken

抓包拿到登录后的 idToken，直接用 Base64 解码（无需私钥即可解码，只是不能伪造签名），个人信息已脱敏：

// Header { "alg": "RS256", "kid": "f10f8740...", "typ": "JWT" } // Payload { "iss": "https://accounts.google.com", "azp": "674187459...apps.googleusercontent.com", "aud": "674187459...apps.googleusercontent.com", "sub": "1041340566***", "email": "z***@gmail.com", "email_verified": true, "iat": 1790735330, "exp": 1790738930 // 有效期 1 小时 }
⚠️
和 MegaHitPoker 的关键区别：这里的 iss 是 accounts.google.com（Google 自己），aud 是原始 Google OAuth Client ID；而 Firebase 签发的 idToken，iss 会是 securetoken.google.com/<firebase项目ID>，并且带一个专属的 firebase 字段。这说明 WSOP 拿到的是 Google 原生 idToken，没有经过 Firebase 转手重新签发。
  • 登录相关请求类型是 fedcm / web-identity —— 这是浏览器原生 FedCM API 的请求，属于 Google Identity Services（不是 Firebase SDK 的请求特征）
  • 没有出现任何 __/auth/handler 或 identitytoolkit.googleapis.com 相关请求
  • 推测 WSOP 自己的后端拿到这个 Google idToken 后，自行验签、自行维护登录会话（可能转换成自己的 session token 或 cookie），登录状态维持逻辑是自研的，不依赖 Firebase

3推荐方案

结合竞品调研结果，WebGL / iOS 场景下的第三方登录，有两条可行路径：

方案一
接入 Firebase Auth
由 Firebase 统一接管 Google / Facebook / Apple 等登录方式，业务侧只对接 Firebase 提供的 SDK 和用户体系。竞品 Mega Hit Poker 采用的正是这条路径。
优势开发成本低、无需自己维护 Token 刷新逻辑、多个登录方式统一管理、有大公司持续维护
需要注意用户体系托管在 Firebase，深度定制会受限于 Firebase 的能力边界
方案二
自研维持登录方案
参照 Firebase 的实现思路（idToken 验签 + refreshToken 静默续期），自己实现一套登录状态维持机制，只在最初的身份验证阶段对接各平台的 OAuth。竞品 WSOP 采用的正是这条路径。
优势用户体系完全自主可控、不依赖第三方服务的可用性和政策变化
需要注意开发和维护成本明显更高，需要自己处理 Token 签发、续期、多端同步等一整套逻辑
方案一的可运行示例 本项目内已经跑通 Firebase Auth 的 Google 登录流程，可直接预览体验
