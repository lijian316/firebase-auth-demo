如何判断 One Tap 是否处于冷却期How to tell whether One Tap is on cooldown

用户关闭 One Tap 卡片后，Google 会按次数递增冷却时间，期间 prompt() 不会再弹出：

After the user closes the One Tap card, Google applies a growing cooldown during which prompt() no longer shows it:

第 1 次关闭1st dismissal2 小时2 hours
第 2 次关闭2nd dismissal1 天1 day
第 3 次关闭3rd dismissal1 周1 week
第 4 次及以后4th and later4 周4 weeks

目前没有稳定的正式 API 可以直接回答"现在是否处于冷却期"，只能间接判断，常见做法有两种：

There is no stable, official API that directly answers “is it on cooldown right now”; it can only be judged indirectly. There are two common approaches:

  1. 看 prompt() 的结果通知（官方，但在被弃用）：调用 google.accounts.id.prompt(callback)，在回调里用 isNotDisplayed() 加 getNotDisplayedReason() 判断，原因为 suppressed_by_user 就表示处于用户关闭后的冷却期。注意：启用 FedCM 后，这类状态方法不再可靠，Google 也在弃用它们，请以 Google 最新文档为准
  2. Read the result notification of prompt() (official, but being deprecated): call google.accounts.id.prompt(callback) and, in the callback, use isNotDisplayed() with getNotDisplayedReason(); a reason of suppressed_by_user means the user-dismissal cooldown is in effect. Note: with FedCM these status methods are no longer reliable and Google is deprecating them, so check Google’s latest docs
  3. 不判断，直接试：每次先调用 prompt()，如果没有弹出（通知为未显示，或等待一小段时间仍无反应），就直接改用 OAuth 弹窗。最简单，代价是需要设一个超时，可能有短暂的等待
  4. Do not judge, just try: always call prompt() first and, if nothing is shown (the notification says not displayed, or nothing happens after a short wait), switch straight to the OAuth popup. The simplest option; the cost is that you need a timeout and there may be a brief wait

保持登录方案 1：缓存后台新签发的 tokenSession persistence option 1: cache the newly issued backend token

前端启动时先看本地有没有后端签发的会话令牌：有就直接用它登录，没有（或被拒绝）才弹出 Google 授权。

On startup the front end first checks for a session token issued by the backend: if there is one it logs in with it directly; only when there is none (or it is rejected) does it open the Google authorization popup.

保持登录方案 2：缓存后台返回的 ID TokenSession persistence option 2: cache the id_token returned by the backend

后端用 code 向 Google 换出 id_token 后，直接返回给前端；前端直接保存这个 id_token，下次带着它登录。id_token 约 1 小时过期，过期后需要重新授权。

After exchanging the code with Google for an id_token, the backend returns it directly to the front end, which stores that id_token and logs in with it next time. The id_token expires after about 1 hour, after which the user has to authorize again.

保持登录方案 3：缓存现有的 gcs_tokenSession persistence option 3: cache the existing gcs_token

登录成功后，前端直接保存并使用现有的 gcs_token；下次启动直接拿它登录，不再依赖 Google 的令牌。令牌失效时才重新走 Google 授权。

After a successful login the front end stores and reuses the existing gcs_token; on the next start it logs in with that token directly, no longer depending on Google’s tokens. Google authorization is only repeated when the token is no longer valid.
