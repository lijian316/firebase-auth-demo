Access Token 方案会把"Google 签名担保身份"降级成"客户端自己上报的数据"，安全性下降，所以推荐采用 Authorization Code 方案。

The Access Token approach downgrades “an identity Google vouches for” to “data the client self-reports” — a real drop in security — so Authorization Code is the recommended approach.

示例：Authorization Code 方案如何拿到并使用 refresh_tokenExample: obtaining and using a refresh_token with the Authorization Code approach

下面是一个最小流程示意（代码里的 ID、令牌都是占位符，不是真实凭据）：前端只负责拿到一次性 code，refresh_token 全程只在后端。

A minimal walkthrough (IDs and tokens in the code are placeholders, not real credentials): the front end only obtains a one-time code, and the refresh_token never leaves the backend.

1前端：弹窗授权，拿到一次性 codeFront end: authorize in a popup and get a one-time code
// 在按钮点击事件里调用// call this from a button click handler const client = google.accounts.oauth2.initCodeClient({ client_id: 'YOUR_CLIENT_ID.apps.googleusercontent.com', scope: 'openid email profile', ux_mode: 'popup', callback: (resp) => { // resp.code 是一次性凭证，只发给自己的后端// resp.code is a one-time credential; send it only to your own backend fetch('/auth/google/exchange', { method: 'POST', body: JSON.stringify({ code: resp.code }) }); }, }); client.requestCode();

⚠️ refresh_token 不是永久有效：用户在 Google 账号里撤销授权、或者长期（约 6 个月）没有使用，续期时会返回 invalid_grant，这时需要让用户重新登录一次。
⚠️ A refresh_token is not valid forever: if the user revokes access in their Google account, or it goes unused for a long time (about 6 months), the renewal request returns invalid_grant and the user has to sign in again.

前端保持登录的完整流程Complete flow: keeping the user signed in

前端启动时先看本地有没有后端签发的会话令牌：有就直接用它登录，没有（或被拒绝）才弹出 Google 授权。

On startup the front end first checks for a session token issued by the backend: if there is one it logs in with it directly; only when there is none (or it is rejected) does it open the Google authorization popup.
