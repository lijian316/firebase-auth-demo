Access Token 方案会把"Google 签名担保身份"降级成"客户端自己上报的数据"，安全性下降，所以推荐采用 Authorization Code 方案。

The Access Token approach downgrades “an identity Google vouches for” to “data the client self-reports” — a real drop in security — so Authorization Code is the recommended approach.

如何判断 One Tap 是否处于冷却期How to tell whether One Tap is on cooldown

用户关闭 One Tap 卡片后，Google 会按次数递增冷却时间，期间 prompt() 不会再弹出：

After the user closes the One Tap card, Google applies a growing cooldown during which prompt() no longer shows it:

第 1 次关闭1st dismissal2 小时2 hours
第 2 次关闭2nd dismissal1 天1 day
第 3 次关闭3rd dismissal1 周1 week
第 4 次及以后4th and later4 周4 weeks

目前没有稳定的正式 API 可以直接回答"现在是否处于冷却期"，只能间接判断，常见做法有三种：

There is no stable, official API that directly answers “is it on cooldown right now”; it can only be judged indirectly. There are three common approaches:

  1. 看 prompt() 的结果通知（官方，但在被弃用）：调用 google.accounts.id.prompt(callback)，在回调里用 isNotDisplayed() 加 getNotDisplayedReason() 判断，原因为 suppressed_by_user 就表示处于用户关闭后的冷却期。注意：启用 FedCM 后，这类状态方法不再可靠，Google 也在弃用它们，请以 Google 最新文档为准
  2. Read the result notification of prompt() (official, but being deprecated): call google.accounts.id.prompt(callback) and, in the callback, use isNotDisplayed() with getNotDisplayedReason(); a reason of suppressed_by_user means the user-dismissal cooldown is in effect. Note: with FedCM these status methods are no longer reliable and Google is deprecating them, so check Google’s latest docs
  3. 前端自己记录关闭时间（推断）：用户关闭 One Tap 时（回调里 isSkippedMoment() 且 getSkippedReason() 为 user_cancel），在本地记下时间和累计次数，再按上面的阶梯（2 小时 / 1 天 / 1 周 / 4 周）估算是否仍在冷却期。缺点：只是估算，看不到 Google 侧的真实状态，用户清除站点数据或换设备就会失准
  4. Record the dismissal time in the front end (inference): when the user closes One Tap (isSkippedMoment() with getSkippedReason() equal to user_cancel in the callback), store the time and a running count locally, then estimate whether it is still on cooldown with the ladder above (2 hours / 1 day / 1 week / 4 weeks). Downside: it is only an estimate, you cannot see Google’s real state, and it drifts if the user clears site data or switches devices
  5. 不判断，直接试：每次先调用 prompt()，如果没有弹出（通知为未显示，或等待一小段时间仍无反应），就直接改用 OAuth 弹窗。最简单，代价是需要设一个超时，可能有短暂的等待
  6. Do not judge, just try: always call prompt() first and, if nothing is shown (the notification says not displayed, or nothing happens after a short wait), switch straight to the OAuth popup. The simplest option; the cost is that you need a timeout and there may be a brief wait
以上是通用做法，并不是 WSOP 的实际实现，WSOP 具体怎么判断冷却期目前未知。这也是上面对比里"方案 3（Authorization Code）"更受青睐的原因之一：它不依赖 One Tap，就不需要判断冷却期。
These are general approaches and not WSOP’s actual implementation; how WSOP detects the cooldown is not known. It is also one reason Approach 3 (Authorization Code) in the comparison above is preferred: it does not rely on One Tap, so there is no cooldown to detect.

前端保持登录的完整流程Complete flow: keeping the user signed in

前端启动时先看本地有没有后端签发的会话令牌：有就直接用它登录，没有（或被拒绝）才弹出 Google 授权。

On startup the front end first checks for a session token issued by the backend: if there is one it logs in with it directly; only when there is none (or it is rejected) does it open the Google authorization popup.
